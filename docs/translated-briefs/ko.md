# ALIGNS.md로 팀에 맞는 코딩 에이전트 학습 데이터 준비하기

엔지니어링 리더, 모델 개발팀, MLOps 팀을 위한 도입 검토 문서입니다.

[English](../team-mlops-brief.md) · [수동 제출 가이드](../team-training-data.md) · [데이터 규격](../../skills/align/references/team-training.md)

## 무엇을 도입하는가

ALIGNS.md는 코드 리뷰와 에이전트 대화에서 팀이 내린 판단을 보존하고, 검토를 거친 사례를 팀의 학습 실험에 넘기는 데 사용할 수 있습니다. 최종 병합된 코드만으로는 알기 어려운 정보가 있습니다. 왜 설계를 줄였는지, 어느 시점에 질문했어야 하는지, 무엇을 확인해야 완료로 인정하는지가 그 예입니다. 당시 맥락과 수정 이유, 승인된 결과를 함께 남기면 이후 학습에 활용할 수 있습니다.

처음에는 저장소나 업무 흐름 하나를 정해 데이터 수집을 시험하는 방식을 제안합니다. ALIGNS.md는 수집 지침, 수동 검토 절차, 로컬 내보내기 도구를 제공합니다. 데이터와 검토자, 학습 모델, 인프라는 팀이 정합니다. 스킬 설치만으로 대화 수집이나 모델 학습이 시작되지는 않습니다.

**현재 준비 수준은 MLOps 팀이 주도하는 데이터 파일럿에 적합한 단계입니다.** 텍스트와 선택된 도구 호출 사례는 특정 토크나이저에서 로딩·토큰 경계 검사를 통과했습니다. 실제 학습기 연결과 코딩 성능 향상은 별도로 검증해야 합니다. 아래에서는 구현 검증과 모델 성능을 구분합니다.

## 어떤 데이터가 쌓이는가

| 출처 | 기존에 남아 있는 정보 | 추가로 보존할 정보 |
| --- | --- | --- |
| 에이전트 대화 | 요청, 제안된 답변, 후속 수정 | 판단 당시 알려진 맥락, 최종 답변의 명시적 승인, 적용 기준 |
| 코드 리뷰 | 패치 논의와 수정 요청 | 어떤 구현이 팀에 적합한 이유, 승인된 패치와 적용 한계 |
| CI·로컬 검사 | 테스트 명령, 출력, 실패 내역 | 기준 커밋, 실행 환경, 해당 패치에 연결된 검증 증거 |
| 팀의 현재 기준 | 합의된 우선순위와 제약 | 기준 버전과 필요한 원문, 변경된 기준의 구분 |
| 처음부터 잘된 결과 | 수정 없이 승인된 산출물 | 명시적인 승인 근거, 수정 대화에만 치우치지 않는 사례 |

유지보수하기 쉬운 구현, API 보존, 적절한 확인 질문, 실제 검증 범위에 맞는 완료 보고가 수집 대상이 될 수 있습니다. 구현 능력을 학습시키려면 승인된 코드나 행동을 확보해야 합니다. “변경 범위를 줄이겠습니다”라는 답변은 응답 방식의 사례이지만, 실제로 변경 범위를 줄인 구현을 보여주지는 않습니다.

팀 기준은 명시적으로 합의해야 합니다. 자주 나온 코멘트나 특정 관리자의 개인 취향을 자동으로 팀의 정답으로 취급하지 않습니다. 개인 기준은 별도 범위로 유지합니다.

## MLOps 팀에 전달되는 파일

| 파일 | 내용 | 용도 | 사용 조건 |
| --- | --- | --- | --- |
| `sft-completion.jsonl` | 입력과 선택된 에이전트 답변·행동 1개 | 판단, 코드 패치, 도구 호출의 SFT | completion-only loss 설정 후 실제 학습 토큰 확인 |
| `dpo.jsonl` | 동일 맥락의 입력, 선호 답변, 비선호 답변 | 선호 최적화 | 사람이 비교를 승인한 텍스트 쌍, 도구 DPO 제외 |
| `evaluation.jsonl` | 학습과 분리한 과제 묶음과 기대 응답 | 팀 기준 또는 실행 기반 평가 | 기대 문장만으로 코드 정답을 판정할 수 없음 |
| `manifest.json` | 출처, 해시, 검토, 제외 이유, 종류별 건수 | 데이터 계보와 감사 | 비공개 메타데이터이며 학습 입력에 넣지 않음 |
| 기존 `sft.jsonl` | 대화와 최종 답변을 합친 텍스트 | 기존 파이프라인 호환 | 과거 답변도 들어 있으므로 새 completion 파일 우선 사용 |

형식은 [TRL 공식 데이터 규격](https://huggingface.co/docs/trl/dataset_formats)에 대응합니다. 입력과 최종 답변을 분리하면 과거의 잘못된 답변을 맥락으로 유지하면서 학습할 정답은 따로 지정할 수 있습니다. 실제 적용 여부는 학습 설정에 달려 있습니다. [TRL의 completion-only loss 설명](https://huggingface.co/docs/trl/sft_trainer#train-on-completion-only)을 함께 확인해야 합니다.

도구 호출 사례는 함수 명세, 화면에 드러난 호출·결과, 학습할 에이전트 행동 1개를 보존합니다. 호출 연결과 함수 이름을 검증하지만, 모든 JSON Schema 인자 제약을 검증하거나 에이전트 실행 전체를 재현하지는 않습니다. 전체 실행 이력 학습과 모델 고유 역할·채널 형식에는 별도 변환기가 필요합니다.

## 0.11.0에서 보완한 구조

[최초 점검](../training-data-readiness.md)에서 확인한 문제를 바탕으로 내보내기와 팀 제출 검증을 보완했습니다. 제출된 승인 기록은 검토 근거이며, 검토자의 신원을 암호학적으로 증명하는 수단은 아닙니다.

| 영역 | 최초 상태 | 현재 구현 | 팀에서 맡을 부분 |
| --- | --- | --- | --- |
| 팀 승인 | 문서상 수동 절차 | 허용 검토자, 정답·비교 승인, 승인 근거, 버전·시각 검사 | 정책 관리와 실제 검토자 인증 |
| 자료 무결성 | 출처 참조 | 제출 파일·개별 기록·증거·산출물 해시 | 저장소 접근 통제와 원본 보존 |
| 판단 맥락 | 학습 입력 밖에만 남을 수 있음 | 필수 문맥 원문 포함 검사와 검토된 입력 해시 | 의미상 충분한 맥락인지, 미래 정보가 섞이지 않았는지 검토 |
| 학습할 정답 | 과거 답변도 SFT 대화에 포함 | 입력과 선택된 답변을 분리 | 실제 학습기의 토큰 마스크와 잘림 확인 |
| 선호 충돌 | 반대 선호쌍도 통과 | 동일 맥락·기준의 선호 순환 거부 | 표현이 다르거나 맥락을 넘는 충돌 검토 |
| 코드 검증 | 자유 서술 | 기준 커밋, 패치, 기록된 통과 검사, 증거 파일 요구 | 격리 환경 재실행과 테스트 범위 판단 |
| 도구 사용 | 텍스트 내보내기에서 거부 | 함수 명세, 호출·결과 연결, 선택된 행동 내보내기 | 인자 규격과 대상 모델의 동작 검증 |
| 학습·평가 분리 | 직접 지정한 과제 묶음, 동일 입력 검사 | 제출 묶음을 넘는 과제 ID, 동일 입력 중복 거부, ID 이름공간 | 유사 과제·의미상 중복 확인 |
| 철회 | 문서상 절차 | 정책에 지정된 기록을 이후 내보내기에서 제외 | 이미 배포한 데이터와 학습 모델의 영향 추적 |
| 잘못된 제출 | 수동 확인 | 쓰기 전 검증, 덮어쓰기 금지, 읽기 전용 검사 | 오류 수정과 승인 근거 보존 |

검증기는 제출된 코드를 실행하거나 모델을 내려받지 않습니다. 코드 증거 검사는 필요한 검증 기록이 존재하고 바뀌지 않았는지 확인합니다. 테스트가 실제로 수행됐는지를 독립적으로 입증하지는 않습니다.

## 이전 벤치마크에서 참고할 수 있는 부분

기존 [확인된 선호 유지 실험](../../RETENTION_BENCHMARK.md)은 판단 기준을 보존하는 효과를 살펴본 자료입니다. 파인튜닝 실험은 아닙니다.

| 조건별 합성 과제 12개의 측정값 | 일반 지침, 선호 학습·저장 가능 | 확인된 선호와 align으로 시작 |
| --- | ---: | ---: |
| 추가 질문 없이 선호에 맞춘 과제 | 3 / 12 | 12 / 12 |
| 과제 수행 중 추가 확인 답변 | 9 | 0 |
| 최종 선호 충족 | 12 / 12 | 12 / 12 |

두 번째 조건에는 첫 번째 조건이 처음에는 몰랐던 선호 정보와 스킬, 검색 지침이 함께 주어졌습니다. 초기 저장 승인 비용은 별도로 답변 4회로 가정했습니다. 이 실험은 파일명의 효과를 분리하지 않고, 같은 정보를 가진 AGENTS.md보다 우수함을 입증하지 않으며, 사람의 실제 시간을 측정하지 않았습니다. [같은 정보를 준 비교 실험](../../DISCOVERY_BENCHMARK.md)은 동률이었습니다.

확인된 기준을 다음 작업에 전달하면 반복 설명을 줄일 수 있는지 시험해 볼 근거입니다. 이를 파인튜닝 성능 향상률, 학습 데이터의 금전 가치나 투자수익률로 바꿔 제시할 수는 없습니다.

## 파일럿 진행과 담당자

| 단계 | 담당 | 산출물 | 완료 기준 |
| --- | --- | --- | --- |
| 범위 결정 | 엔지니어링 리더·참여자 | 대상 업무, 합의 기준, 허용 출처, 비공개 제출 위치 | 무엇을 어떤 용도로 모으는지 참여자가 이해 |
| 후보 수집 | 동의한 참여자·에이전트 | 진행 중 작업 또는 선택된 기록의 후보 | 실제 맥락, 답변, 가능한 증거 보존 |
| 수동 제출 | 참여자 | 선택한 자료와 파일 목록 | 정확한 제출 파일과 사용 범위 확인 |
| 검토 | 지정 검토자 | 정답·선호쌍 승인, 공유 과제 ID | 미해결 판단을 정답으로 넣지 않음 |
| 검증·내보내기 | MLOps | 버전이 붙은 데이터와 manifest | 규격 검사 통과, 제외 내역 검토 |
| 학습 연결 | MLOps | 고정된 학습 환경과 승인된 시험 실행 | 마스크, 잘림, 실행 재현성 확인 |
| 평가 | 엔지니어링 검토자·MLOps | 독립 과제 결과와 회귀 보고 | 학습 전에 합의한 도입 기준 충족 |

주간 또는 스프린트 단위로 제출할 수 있으며 주기는 팀이 정합니다. 중요한 판단이 발생할 때 후보를 남기고, 이미 받은 승인을 재사용합니다. 빠진 정보만 묶어서 검토하고, 실제 제출은 사람이 수행합니다. 개인별 제출 건수 할당은 두지 않는 편이 좋습니다.

## 양을 늘릴 때 관리할 지표

| 지표 | 정의 | 판단에 쓰는 방법 |
| --- | --- | --- |
| 승인 수율 | 승인된 고유 사례 / 검토한 후보 | 필요한 사례가 수집되는지 확인 |
| 검토 효율 | 승인된 고유 사례 / 검토 시간 | 수고가 줄었는지 다른 사람에게 옮겨졌는지 확인 |
| 과제 범위 | 기준·업무·난도별 서로 다른 과제 묶음 | 추가 수집이 필요한 영역 선택 |
| 증거 완성도 | 재실행 자료를 갖춘 코드 후보 / 코드 후보 | 구현 사례의 검증 가능성 판단 |
| DPO 적합률 | 승인된 동일 맥락 쌍 / 검토한 비교 사례 | 선호 학습에 적합한 자료량 확인 |

목표값은 파일럿의 비용과 목적을 보고 정합니다. 일정 건수에 도달했다고 학습 준비가 끝난 것은 아닙니다. 생성한 변형 사례는 부족한 영역을 보완하는 용도로 쓰고, 원본 과제와 연결하며, 실제 관찰 자료와 구분합니다. 같은 사례를 다르게 쓴 문장들을 독립된 근거로 세지 않습니다.

## 학습한 모델의 도입 판단

같은 ALIGNS.md와 도구, 작업 예산을 사용해 기본 모델과 튜닝 모델을 비교합니다. 변형 자료를 만들기 전에 과제 묶음별 분리를 정합니다. 검증 결과로 모델을 고른다면 최종 시험 과제는 별도로 남깁니다.

코드 정확도, 불필요한 질문, 변경 범위, 완료 보고, 검토자의 수정을 함께 측정합니다. 일반 코딩 과제와 변경된 팀 기준에서도 성능이 후퇴하지 않았는지 확인합니다. 통계는 문장 변형 수가 아니라 과제 묶음 단위로 보고, 표본이 작으면 불확실성을 명시합니다.

수정 횟수가 줄어도 코드가 나빠졌다면 성공으로 판단하지 않습니다. 현재 코드와 바뀐 기준은 실행 시점의 맥락으로 계속 전달해야 할 수 있습니다. 파인튜닝한 모델이 ALIGNS.md 변경을 자동으로 학습하는 것은 아닙니다.

## 도입 범위와 남은 책임

수집·내보내기 구성요소는 저장소의 MIT 라이선스로 제공됩니다. 이 라이선스가 참여자의 코드·대화나 제3자 자료에 대한 사용 권리를 부여하지는 않습니다. 학습 용도, 보존 기간, 제공업체는 팀이 결정합니다. 출처와 검토 정보가 든 manifest도 선택한 기록과 같은 수준으로 관리해야 합니다.

우선 제한된 데이터 파일럿을 수행하고 대상 모델의 학습 연결을 점검하는 단계까지 진행할 수 있습니다. 검토자 인증, 의미상 충돌 해소, 격리된 코드 재실행, 호스팅된 제출 서비스, 실제 운영 효과 측정은 현재 구현에 포함되지 않습니다. 수집을 중단해도 기존 ALIGNS.md 합의를 바꿀 필요는 없습니다.
